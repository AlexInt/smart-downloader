01总览与 ER 关系图

六张表住在同一个文件里。drama_cache 与 drama_episodes 由 DramaCache 维护（站点元数据镜像）； episode_actions 与 local_actions 由 EpisodeActionsStore 维护（用户行为数据）； drama_related 由 DramaCache 写快照；drama_favorites 由 DramaFavorites 维护（剧级收藏）。 两组表没有外键约束，关联靠「同一套主键字段 + 代码约定」，删除时的联动由代码显式执行。 建表与版本迁移统一在 Drama/DramaDatabase.swift：整库只有一个 user_version， 两个 Service 各管一段会互相跳过对方的建表，所以谁开库都走同一个入口。

v2 新增（详情接口整包落库）：drama_cache 加 api_detail（原始响应体整包）+ 34 个提升列， drama_episodes 加 8 个每集元数据列，新增 drama_related 存推荐剧快照。 此前详情接口只有 tags 被收集，其余 39 个顶层字段解码后即丢弃 —— 现在整包留存，提升列只为查询方便。
v3 新增（剧级收藏入库）：drama_favorites 表（键 (site, drama_id) + created_at）。 收藏是「关系」数据，入库后可与 drama_cache / episode_actions / drama_related JOIN （基于收藏的本地推荐、最近收藏排序）。旧 UserDefaults 键 DramaDetail.favorite.* 一次性搬入，读路径永远走库。

为什么是「id 主表 + 路径兜底表」两张行为表： 剧集页入口带着 (site, drama_id)，能精确定位到服务端 episode_id， 于是点赞 / 收藏 / 播放位置都能挂在稳定的 id 上（重新下载、改目录、改名都不丢历史）， 并且可以和 drama_episodes JOIN 出「看到第几集」「哪些集收藏过」。 但散装 HLS、普通 mp4、以及从没进过剧集页缓存的历史条目根本没有服务端 id， 硬造一个 id 会把数据挂到别的集上，所以它们走 local_actions，以资源路径为主键。
维度现状
库文件位置Documents/drama_cache.sqlite3（Finder 文件共享可见可拷出）；设了环境变量 SMARTDOWNLOADER_DIR 时改写到该目录下（冒烟隔离用）
打开方式sqlite3_open_v2(path, READWRITE | CREATE)，每次调用开一次、用完 sqlite3_close
事务批量写包在 DramaDatabase.transaction 里（saveDetail 一次事务写整包 + 提升列 + 每集元数据 + 推荐快照；saveInfo 一次事务写剧信息 + 集清单合并）；单条写各自 autocommit。事务不查中间语句结果、失败不 ROLLBACK（缓存场景可接受，失败形态是部分提交）
索引只有主键自带的索引，没有额外 CREATE INDEX；按 name 反查剧是全表扫（剧数量级小）
日志模式默认（未开 WAL）；未设 busy_timeout
外键未声明 FOREIGN KEY，未开 PRAGMA foreign_keys；一致性由代码保证
时间字段一律 ISO8601DateFormatter().string(from: Date()) 的 TEXT，非 Unix 时间戳
布尔字段SQLite 无 BOOLEAN，用 INTEGER 0/1
错误处理失败打印 CACHE FAIL[...] + sqlite3_errmsg，不静默；读失败返回 nil / 空集

接口返回的集清单镜像 + 下载状态。「是否已下载」的账本是磁盘（playlist.m3u8 存在即已下载）， 本表是它的镜像：下载完成立即 markDownloaded，选集面板每次打开 reconcileDownloaded 对账。

04表 3 · episode_actions（集级行为数据 · 主表）

维护方 Drama/EpisodeActionsStore.swift。一集一行、列即行为： 点赞、收藏、上次播放位置，以及后续要加的行为字段都加在这张表上。 主键与 drama_episodes 完全同构，所以能直接 JOIN 做关系查询。 行是「按需出现」的：只有真的点赞 / 收藏 / 播过，才会有这一行。

字段类型约束 / 默认含义与取值写入时机读取方
siteTEXT PK 1 NOT NULL 站点 origin，与 drama_cache / drama_episodes 同值 点赞 / 收藏：用户点按即时 upsert（setLiked / setSaved）

播放位置：只在关键时机 upsert（savePosition）—— 暂停、拖完 seek、切集、退出播放页、App 进后台；播放过程中只攒内存不写库

删除资源：removeActions 整行 DELETE 		播放页续播与状态回填（actions(for:)）

已下载列表 / 剧详情页副行（episodeActions(site:dramaID:) 按剧一次读全）

后续可做：看到第几集、收藏清单、未播完清单（JOIN 查询）
drama_idTEXT PK 2 NOT NULL 站点侧剧 id
episode_idINTEGER PK 3 NOT NULL 服务端集 id。由 MediaIdentity.episode 带入；重新下载 / 改目录 / 改名都不影响它
likedINTEGER NOT NULL DEFAULT 0 点赞（0/1）。播放页右侧点赞按钮的状态
savedINTEGER NOT NULL DEFAULT 0 收藏（0/1）。播放页右侧收藏按钮的状态。注意与剧级收藏区分：剧级收藏在 UserDefaults 的 DramaDetail.favorite.*
position_secondsREAL NOT NULL DEFAULT 0 上次播到的秒数（浮点，保留小数）。0 表示没播过或从头开始
position_totalREAL NOT NULL DEFAULT 0 该资源总时长（秒）。0 = 时长未知：此时不计算进度比例、不判「已看完」
updated_atTEXT可空 ISO8601，本行最近一次写入时间。做「最近观看」排序时用它（目前尚未用于排序） 
CREATE TABLE IF NOT EXISTS episode_actions (
    site TEXT NOT NULL,
    drama_id TEXT NOT NULL,
    episode_id INTEGER NOT NULL,
    liked INTEGER NOT NULL DEFAULT 0,
    saved INTEGER NOT NULL DEFAULT 0,
    position_seconds REAL NOT NULL DEFAULT 0,
    position_total REAL NOT NULL DEFAULT 0,
    updated_at TEXT,
    PRIMARY KEY (site, drama_id, episode_id)
);
派生口径（在 PlaybackProgress / Actions 里，不落库）： 进度比例 fraction = clamp(position_seconds / position_total, 0, 1)； 已看完 = position_total > 0 且 position_seconds ≥ position_total − 5。 续播条件 = 已播 > 3 秒、未看完、且 position_seconds < 当前总时长 − 5；不满足就从头播（时长变短 / 已到片尾都从头）。

05表 4 · local_actions（本地资源兜底表）

同一套行为字段，但主键换成资源文件的相对路径。 用于「拿不到服务端集 id」的资源：散装 HLS 条目、普通视频文件、以及从没进过剧集页缓存的历史条目。 与 episode_actions 互不覆盖：一条资源只会落在其中一张表里，读取侧按「先 id 后路径」兜底。

字段类型约束 / 默认含义与取值写入时机读取方

普通文件 /xxx.mp4

播放页续播（actions(for: .localPath)）
likedINTEGER NOT NULL DEFAULT 0 点赞（0/1）

CREATE TABLE IF NOT EXISTS local_actions (
    media_path TEXT NOT NULL PRIMARY KEY,
    liked INTEGER NOT NULL DEFAULT 0,
    saved INTEGER NOT NULL DEFAULT 0,
    position_seconds REAL NOT NULL DEFAULT 0,

路径键的代价：文件被移动 / 重命名 / 重新下载到不同目录，这条记录就认不出来了（id 主表没有这个问题）。 另外删除资源时必须显式 removeActions，否则库里留下永远读不到的死行 —— 现在 delete(at:) / deleteSeries / deleteTasks(ids:) 三条删除路径都已接上清理。

05c表 6 · drama_favorites（剧级收藏）

一行 = 一部被收藏的剧。v3 起从 UserDefaults 的 DramaDetail.favorite.<site>#<dramaID> 布尔键搬进库：收藏 = 有行，取消 = 删行。入库的理由是「关系」—— 可与 drama_cache（剧名/封面）、episode_actions（看到哪集）、drama_related（推荐来源）JOIN， 散在 UserDefaults 里建不起这些查询（AGENTS.md 架构约定第 6 条同一判据）。 维护方 Drama/DramaFavorites.swift；本表不冗余存展示字段，剧名等一律 JOIN 取。

字段类型约束含义与取值写入方读取方
siteTEXTPK 1 NOT NULL剧集站点 origin（scheme://host[:port]），与 drama_cache.site 同一套身份setFavorite / v3 旧键搬迁isFavorite / favoriteDramas
drama_idTEXTPK 2 NOT NULL剧 id（服务端 video_id 的字符串形式）同上同上
created_atTEXT可空ISO8601 收藏时间。重复收藏会刷新（视为最近一次动作），供「最近收藏」倒序setFavorite（true 分支）/ 搬迁写当前时间favoriteDramas（ORDER BY created_at DESC）
CREATE TABLE IF NOT EXISTS drama_favorites (
    site TEXT NOT NULL,
    drama_id TEXT NOT NULL,
    created_at TEXT,
    PRIMARY KEY (site, drama_id)
);
API：isFavorite(site:dramaID:) 判存在、setFavorite(_:site:dramaID:) 插/删、 favoriteDramas() 返回按收藏时间倒序的三元组（收藏列表与本地推荐算法的入口）。 旧 UserDefaults 键保留不清，读路径永远走库（迁移细节见 8.3）。 与每集收藏（episode_actions.saved）是两个维度：整剧 vs 单集，不共享存储。

05d详情接口整包落库：采集时机与三种响应形态

采集方 Drama/DramaMetaHarvester.swift：隐藏 webview 加载剧集页，注入响应捕获脚本， 命中详情响应即调 DramaCache.saveDetail。

项现状
采集时机15 天新鲜度闸门（用户拍板 2026-11-13，取代「每次进页都抓」）：detail_fetched_at 在 15 天内不重抓（DramaCache.detailFetchedAt + harvestIfNeeded(force:)）；过期、↻ 刷新按钮 force、或 coverMissing（详情有记录但封面文件没落盘）时重抓。同一次访问内由 hasHarvestedThisVisit 挡重复；注意 force 必须绕过去重标记（原实现 force 被 hasHarvestedThisVisit 前置吞掉，已改为 !hasHarvestedThisVisit || force）
响应形态 1 · plain明文详情 JSON → 直接解码，api_detail 存响应体原文
响应形态 2 · envelopeapi.php 加密信封（errcode=0 + data base64）→ DramaSession.decryptCapturedBody 解密后解码，api_detail 存解密后的 JSON
响应形态 3 · payloadNuxt _payload.json（槽位数组）→ DramaDetailData.fromNuxtPayload 解引用后解码，api_detail 存结构化回写（字段以模型为准）
校验解码出的 video_id 必须等于目标剧 id，否则丢弃并打 videoIdMismatch 日志
事务剧级 upsert + N 集 upsert + 推荐快照替换包在一个事务里（DramaDatabase.transaction）
调查落盘捕获数组仍写 Documents/DramaMeta/api_<site>_<dramaID>.json，DOM 结果写 harvest_*.json，页面 HTML 写 html_*.html
为什么整包 + 提升列两条腿：整包保证「站点加字段不用改代码也不丢数据」， 提升列保证「能按播放量排序、能 JOIN、能直接展示」。只存整包就无法按字段查询，只拆列则站点一变就要迁移。

06drama_cache.page_meta 的 JSON 内部字段

这一列是 TEXT，里面存 JSON。savePageMeta 采用合并式覆盖：读出旧 JSON、把本轮字段并进去、再整体写回， 所以历史字段不会被本轮没抓到的字段冲掉。字段来自两处：DOM 提取脚本 dramaMetaJS 的返回值，以及收割器补充的派生字段。

JSON 键类型来源含义
urlstringDOM：location.href提取时的页面地址
titlestringDOM：document.title页面标题（可能带营销后缀）
ogImagestringDOM：meta[property=og:image] → twitter:image封面候选；非空时同时写入 cover 列
ogTitlestringDOM：meta[property=og:title]OG 标题
keywordsstringDOM：meta[name=keywords]页面 keywords（调查用）
descstringDOM：meta[name=description] → og:description简介候选；非空时同时写入 intro 列
imgsstring[]DOM：前 40 个 img 的 currentSrc/src页面图片列表（调查用）
textstringDOM：body.innerText 压空白后前 500 字正文摘要（调查用）
coverstring收割器派生ogImage 非空时补写，与 cover 列同值
introstring收割器派生desc 非空时补写，与 intro 列同值
page_titlestring收割器派生title 非空时补写（保留原始标题，便于和清洗后的剧名对照）
tagsstring接口拦截（DramaSession 解密响应）标签数组 join(" ")，同时写入 tags 列
tags_sourcestring收割器写入目前只有 "api" 一种取值。nil（旧缓存）视为缺失，进页会自动补采一次
tags 的空值约定：抓不到标签时写 NULL、绝不写空串。空串会被 ViewModel 当成「已缓存」而永久跳过补采 （这是修过的一个真实 bug）；历史脏数据里的空串也一律归为「无」。

07键规则与身份解析

7.1 MediaIdentity：一条资源属于谁

enum MediaIdentity: Hashable {
    case episode(site: String, dramaID: String, episodeID: Int)   // → episode_actions
    case localPath(String)                                      // → local_actions
}

解析口径只有一处：EpisodeActionsStore.identity(...)，播放队列、下载列表、删除清理三方共用，避免「写到 A 读到 B」。

入口拿得到的身份解析路径落到哪张表
剧集页点已下载集 → 沉浸式播放 DramaTarget(site, dramaID) + ApiDramaEpisode.id ImmersivePlaybackRequest.target 直达 → DramaCache.seriesIdentity(site:dramaID:) 取「集号→集 id」映射 episode_actions（无歧义）
下载页 → 剧详情页点集播放 只有剧名 + 目录名「第NN集」 DramaCache.seriesIdentity(forSeriesName:) 按 name 反查（ORDER BY fetched_at DESC 取最近一条），再用 episodeSort(fromFolderName:) 解析集号 反查命中 → episode_actions；未命中 → local_actions
下载页主列表点条目（AVKit 播放） 剧名 + 目录名，或什么都没有（散装） 同上；seriesName == nil 时直接用资源路径 散装 / 普通文件 → local_actions
磁盘扫描收编的历史条目 只有文件路径 该剧若从没进过剧集页缓存，库里查不到 → 退回路径 local_actions

规则实现说明

08建表与迁移历史

8.1 统一迁移入口（v2 起）

user_version 是整库一个计数器。此前 DramaCache 与 EpisodeActionsStore 各自建表， 谁先开库谁先抬版本号，就会跳过对方的建表/搬迁 —— 所以 v2 起把建表与迁移集中到 Drama/DramaDatabase.swift，两个 Service 的 openDB() 都只调 DramaDatabase.open()。

步骤做什么幂等策略
1 建表CREATE TABLE IF NOT EXISTS 六张表 + tags 列「先查再补」ALTER天然幂等
2 补列逐列查 PRAGMA table_info，缺哪列 ALTER 哪列（drama_cache 36 列 = api_detail + detail_fetched_at + 34 个提升列、drama_episodes 8 列）不靠版本号判断列是否存在：即使版本号被别的入口提前抬高，缺的列也补得上
3 搬旧数据把 UserDefaults 里的集级点赞/收藏/进度搬进行为表（见 8.2）；把剧级收藏搬进 drama_favorites（见 8.3）各用独立标记门控（EpisodeActions.legacyMigrated / DramaFavorites.legacyMigratedToSQLite），与 schema 版本解耦，避免「版本已抬高 → 搬迁被跳过」丢用户数据
4 记版本PRAGMA user_version = 3只在低于当前版本时写
版本内容
v1episode_actions / local_actions 两张行为表 + 旧 UserDefaults 行为数据搬迁
v2详情接口整包落库：drama_cache 加 api_detail 与 34 个提升列、drama_episodes 加 8 个每集元数据列、新增 drama_related
v3剧级收藏入库：新增 drama_favorites（键 site + drama_id，created_at 供「最近收藏」排序）+ 旧 UserDefaults 收藏搬迁（独立标记门控）

8.2 v0 → v1：把散在 UserDefaults 的行为数据搬进库

旧 UserDefaults 键旧值形态搬到规则

8.3 v2 → v3：剧级收藏从 UserDefaults 搬进 drama_favorites

SELECT c.name, e.sort, a.position_seconds, a.position_total

  AND a.position_seconds < a.position_total - 5

11已知取舍与风险

#事项影响现状 / 可选改法
1按剧名反查身份有歧义 两部剧同名（或同剧多站点）时，下载页入口与剧集页入口可能落到不同记录 已打 AMBIGUOUS 日志、取 fetched_at 最近一条。彻底解法：下载时把 (site, drama_id) 落到条目上（drama_episodes 已有 folder 可对应），不再靠名字猜
2播放中只攒内存 进程被硬杀时，最多丢最后一段没 flush 的位置 已覆盖暂停 / seek 收尾 / 切集 / 退出 / 进后台五个时机；要更稳可加定时 flush（代价是写库频率）
3saveInfo 先删后插（已修复） 曾把刷新集列表的 downloaded/folder 清成 0/NULL 2026-11-12 改合并式落库：按 id upsert + 只删接口已不存在的集；同列表刷新与列表变化场景均已冒烟验证
4无外键、无级联 直接改库不会联动；一致性完全靠代码 删除资源的三条路径已显式清行为数据。若要强约束可加 FOREIGN KEY + PRAGMA foreign_keys=ON（需评估旧库兼容）
5无额外索引 WHERE name=? 反查是全表扫 剧数量级小，暂不加；量大时 CREATE INDEX idx_drama_name ON drama_cache(name)
6未开 WAL；部分批量写仍无事务 reconcileDownloaded 逐集 UPDATE = N 次 autocommit，集数多时偏慢 saveDetail 已包在一个事务里；reconcile 可同样处理，读多写少场景可评估 WAL
7路径键脆弱 local_actions 的记录在文件改名 / 移动 / 换目录重下后认不出来 这是「没有服务端 id」的必然代价；能进剧集页缓存的集会自动升级到 id 主表
8主线程 IO 所有读写在主线程（与 DramaCache 同约定） 列表侧已收敛为「按剧一次读全 + 本地表一次读全」，不再逐行开库
9position_total = 0 表示时长未知 此时不显示进度比例、不判「已看完」 刻意设计：避免把「未知」当成 0% 或 100%
10提升列与整包可能不同步 提升列是写入时的快照，整包才是权威 两者同事务写入，正常路径一致；手工改库时以 api_detail 为准
11payload 形态的整包是结构化回写 Nuxt _payload.json 是槽位数组，回写后只含模型声明的字段 明文/信封形态存的是真原文；payload 形态若出现模型未声明的新字段会丢，需要时补模型
12剧级聚合未落列 「看到第几集」目前只能实时 JOIN 算 表已支持（见 10.2）；要做剧行展示或最近观看列表时再决定要不要冗余列
